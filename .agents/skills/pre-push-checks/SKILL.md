# 按改动选择检查

检查应覆盖实际改动的行为，并保留可核对的证据。命令与最小验证矩阵以[开发流程](../../../docs/development.md#验证)为准，RAG 专属入口见[模块说明](../../../rag/README.md#数据获取与验证)，不另建聚合检查脚本或复制完整命令清单。

## 确认范围

先用 git status、分支和完整差异确认工作区、暂存与未暂存改动。准备推送时还要确认真实远端目标／PR基准，检查相对该基准的全部待发布提交，不能只看最后一次提交，也不能猜基准一定是 main。只作本地交付时不为凑流程联网、提交或推送。

## 选择和复用证据

- 文档或 skill：核对命令与当前源码、路径／锚点和完整差异，执行预算门禁；skill 另做结构及独立应用验证。普通文档修字不默认运行全量RAG测试或真实模型。
- Python／检索行为：先选能观察目标回归的所属测试，公共约束改变时覆盖受影响调用方。新增检查须有能失败的负例。使用 uv；默认离线合成输入，不以全量本地数据、模型或网络服务作为单测前提。
- catalog／基线引用：核对指纹与元数据；明确本机资料是否存在，不能将新克隆缺数据算成CI失败，也不能借检查修改／提升基线。真实评测和发布按任务范围执行。
- CI／资源型测试：先按 [ci-test-reliability](../ci-test-reliability/SKILL.md) 确定隔离、恢复、清理及并发证据，再选命令。性能取舍使用 [speed-up-perf](../speed-up-perf/SKILL.md)，不因一次耗时就加门槛。

给出具体命令前核对脚本、参数和测试类／方法实际存在，确认筛选确实选中目标用例。记录命令、针对的源码／输入、退出码与结果；测试另记选中数量，静态检查标明不适用。已针对最终内容通过的检查不因提交或交付再次重跑；后续修改或基准合并使相关证据失效时，只重跑受影响部分。用户要求全套检查或实际跨模块影响时再扩大范围。

## 交付或推送

相关检查失败时，先修复或报告准确阻塞；不要隐藏失败、跳过hook或等CI“碰巧通过”。只有本地实测才能声称本地通过，远端CI按实际状态报告通过、失败、跳过或待完成。检查暂存清单、鉴权内容和忽略规则，避免将原始数据、回答及派生报告纳入提交。

授权推送时再执行推送并核对远端HEAD；授权改写历史时使用事先观察到的远端OID做精确lease保护，不用裸force。没有对应授权就完成本地交付，不以本skill要求额外请求发布许可。报告变更、实际检查、未验证项与剩余问题，不把程序完成或引用合法当成语义／用户验收通过。
