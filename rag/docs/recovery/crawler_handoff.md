## 目标

恢复快照内可见的中文游戏剧情文本：对白、选项、旁白、角色故事与语音、书籍及物品设定。保留原文、来源、场景和原文明确的分支结构，尽量提高恢复率。

原始层完整保存，不等于所有Wiki页面和参数都应成为剧情正文。游戏机制、攻略、Wiki吐槽、页面样式和索引应单独标记；角色的战斗语音、剧情力量和数值形式的叙事不能仅因出现战斗词或百分数就删掉。

不调用LLM补正文、猜说话者、推分支或裁定事实。页面缺失、引用未缓存、图片文字未包含在快照中，登记needs_source。目标是已保存来源的恢复与忠实记录，不是声称整款游戏100%覆盖。

## 已验证的根因与优先级

### 1. 页面身份及同名覆盖

`tools/batch_character_quests.py` 当前按解析后的任务名称写文件、聚合并判断resume。四个幕间小憩原页面ID分别为157520、157524、157550、157576，但解析名称都为“幕间小憩”；后日谈和基尼奇也有原页面完整标题与展示名不同的情况。

- 页面ID和完整原页面标题作身份，任务名称仅作展示；不删除括号、日期或链接目标的消歧信息。
- 同时修复存储键、聚合键、resume判断、排序和索引引用，不仅修改文件名。
- JsonFileStore继续按完整原页面标题生成安全文件名。多个页面可以有同样的展示名称，但不能覆盖或以别名自动合并。
- 来源身份不存在时不以null为共同主键；缺失页面不能生成“已恢复”正文。
- 重定向与别名记录来源映射，歧义和循环显式报告，不能自动选第一个候选。

### 2. 显示模板和剧情容器

本地解析器已经含部分颜色、折叠、注音、人物对话及剧情选项处理，需修复调用路径、遗漏容器和元字段，不应再造重复功能。只读实验中，月夜，泊船码头原页明确有对白，但当前parse_event_quest_page仍得到0组0条；古老的考察日志正文仍留有未展开模板。

- 支持`<big>`等明确显示标签，保留内部文字。多数现有流程异常只是`<big>`或颜色包装，不该因此丢整组台词。
- 处理颜色、折叠、注音、人物对话及已经确认语义的其他模板。每类规则有真实样例，不能将任意模板的所有参数无区别拼入正文。
- 支持标题组织的剧情，以及`{{剧情}}`参数里的章节、段落名、`内容1.3`等正文；空段落保留结构，不编内容。
- 在场景、说话者、正文等各字段一致执行已确认的显示清理，不能只清正文而将`{{#tag...}}`当人物姓名。
- 未知模板保留源块并报告，不删除后把页标成完整成功。Wiki吐槽、攻略、CSS和游戏正文分开处理。

### 3. 分支先结构化，后兼容展平

当前`_render_event_quest_option_template`把各选项和各分支文字依次拼成字符串；现有ArchonQuestDialogue/EventQuestDialogueEntry没有保存分支归属。文字出现并不表示结构正确。

- 在展平前提取剧情选项、tabber及已确认条件结构，保留选项对应的对白、嵌套选择路径、来源明确的性别／条件分支。
- 不把A/B的回应串成唯一路径，不创造原文没有的连接或顺序。
- 重复标题、重复台词保留真实位置；不能用字符串第一次find代替当前节点位置。
- 保留“？？？”、空说话者、玩家名占位符和未解决结构，不用后文反向猜名。
- 普通线性段落的已确认空分支路径，与结构未解决的null/未解决状态要区分。

### 4. 辅助页面消费和空字段

474份“没有独立parsed文件”的原页并非474份漏剧情。启发式分类包含121份语音辅助页、153份系列／索引候选、9份任务正文候选、22份含剧情模板的其他页、164份其他入口／资料页、4份重定向及1份非正文命名空间页；这些是路由线索，不是语义验收。七七语音已合并到角色记录，不能再次算作全页漏解析。

- 登记角色对语音页、业务页对模板和引用页的依赖及消费关系。来源定位落到真正提供文字的页面，而不只是合并后的角色文件。
- 模板页可以提供业务页面所需文本，不仅凭namespace排除；无关联的示例模板和填写提示不作剧情。
- 区分合法空值、原文有内容但解析遗漏、依赖缺失、暂不支持。普通道具内容为空不自动等于漏剧情。
- 活动入口或系列页中若有实际剧情，要提取相应部分；其他结构只作索引／元信息，不重复造正文。


**此入口目前是待实现命令，不能宣称已经可用。** 完全离线为本实验硬边界：不初始化会联网补依赖的批处理路径，不自动crawl、不请求渲染API、不下载媒体、不调用模型。只读解析API可直接复用；HTTP或模型访问应在测试中触发失败。

输出根必须位于输入与项目共享原始数据之外，不覆盖任何已有RAG、raw或历史样本。输出兼容业务parsed、新的权威`text_units.jsonl`、候选节点清单、未解决来源／规则清单及简短恢复摘要。不要靠覆盖旧数据假装恢复成功。

文本单元最低字段为`unit_id、type、text、speaker、scene_id、branch_path、source`。type区分对白、选项、旁白、语音、故事、书籍和描述；Wiki整理与游戏摘录的来源性质另外明确标注，不把编年史推测写成官方原文。

- source记录原页面ID、完整标题、原文件、WikiText哈希及原文定位；定位采用解码WikiText字符串的零基半开字符范围。
- scene_id来自原文场景结构；branch_path记录选择组、选项ID、标签和原文明确条件。未知归属使用未解决状态，不当作确定线性流程。
- 从范围可以确定性重放显示清理，文本不被重新总结或改写。source定位必须指向当前真实节点，重复内容不共用第一次匹配位置。
- unit_id按来源身份和位置生成，同输入／配置稳定。一个来源节点可以被多个业务记录消费，但覆盖统计按来源节点去重。
- 旧展平数组保留兼容用途，新文本单元是来源与分支的权威输出。后续RAG必须按来源、场景、分支分组，不可继续从旧数组混拼已恢复的分支。

## 独立校验及实验顺序

1. 冻结输入，核对提供的哈希基线；在自己的实现工作区先检查Git状态。
2. 根据regression_cases.json建立真实回归测试，补嵌套选择、同一句多次出现、依赖缺失和重定向循环等受控样例。旧parsed不是正确答案。
3. 先修页面身份、显示清理、剧情容器及分支导出，使代表页面通过原文和结构检查。
4. 用同一快照全量离线重解析，输出新目录，再重复运行验证稳定性和原始哈希不变。

独立源清单列出候选中文文本节点，校验器逐项记为已导出、作为元信息消费、明确非剧情、需要依赖或尚未支持。未知节点不能从分母消失。不要共用被测解析器核心逻辑去“证明没有遗漏”，也不能只以to_dict正常返回或对白数增加判成功。

摘要按恢复价值汇总问题类别和受影响页面，附每类少量代表原文；机器保留详细节点和来源。用户只需评审规则及代表样本，不需逐页处理数百条清单。

分别报告文本恢复率、已导出文本的来源保真、分支结构检查和未解决数量。源码没有的内容、媒体文字和未缓存依赖必须单独列出，不假装是合法空值，也不通过模型补全压低缺口数。
